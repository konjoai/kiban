# KT-14.1 -- Can the new task-to-diff loop produce diffs whose classification agrees
more often than it disagrees, at a scale a 3-run protocol can afford?

**Verdict: PASS.** 8 of 9 real, live sessions produced a diff; every task where more
than one run succeeded produced byte-for-byte-identical per-class defect counts across
its repeats. The one place this run found real non-determinism was NOT classification
noise -- it was a single session that completed cleanly (exit 0) but wrote no diff at
all, a distinct failure mode from "the classifier disagreed with itself," named below
rather than folded into the same number.

## Procedure

Built the real loop this kill-test exists to gate (`lib/gen_runner.py`,
`evals/gen_cassettes.py`, `bin/konjo-eval genrun` -- Phase 14, Phase 1), then ran it
for real against `konjoai/lopi` (cloned read-only this session, unshallowed for real
commit history): 3 tasks, each drawn from real closed lopi work (git log, not
invented), each run 3 times under identical context (baseline: no `--append-system-
prompt` override, ambient repo `CLAUDE.md` auto-discovery only -- see
`lib/gen_runner.py`'s module docstring for why this backend does not use `--bare`).
Each task's prompt describes a real pre-fix defect confirmed by reading the parent
commit's actual source (not the eventual fix diff, and not invented):

| Task | Real source commit | Defect class it targets |
|---|---|---|
| `lopi-bound-unbounded-channels` | `f149113` (parent `557c2ff`) | `unbounded_queue` |
| `lopi-explicit-whatsapp-dev-override` | `f79c319` (parent `d12329e`) | security override clarity |
| `lopi-typed-errors-sqlite-pool` | `cc51f40`, scoped to one file (parent `f149113`) | `untyped_error_boundary` |

Each of the 9 sessions ran in its own isolated `git worktree` (never the caller's own
checkout, never pushed), `claude -p` invoked non-bare with `--permission-mode
acceptEdits` and an explicit tool allowlist (`Read,Write,Edit,Bash,Grep,Glob` -- no
`WebFetch`/`WebSearch`), `--max-budget-usd 2.0`, told explicitly not to run
`cargo build`/`test`/`check` (keeps each session's wall time bounded to the edit
itself). Every resulting diff was classified with `evals/genfixtures.classify_diff`
(the same Phase 2-extended, 7-of-8-mechanical classifier this sprint closed the gap
on) and saved as a real fixture under `evals/gen_fixtures/` is NOT where these landed
-- they are recorded separately (`/tmp/kt14_1_out/`, not committed) since they are
KT-14.1 evidence, not the seed corpus; the seed corpus additions this sprint
(`04`-`07`) are hand-authored illustrative fixtures, a distinct and already-labeled
category (see `evals/genfixtures.py`'s module docstring and `LEDGER.md`'s
`Gen-Fixtures-1`).

## Raw results (real, 2026-07-29, kiban branch `claude/kiban-phase-14-harness-7anoxd`)

**Numbers below are post-fix, re-classified with the corrected classifier -- not the
numbers this run first produced.** The first pass through `evals/genfixtures.classify_diff`
reported `lopi-bound-unbounded-channels`'s two successful runs as
`unbounded_queue=1, untrusted_input_reaching_exec=1` each. While building Phase 3's
comparison (below), the exact same shape turned up in that data too and was traced to
its cause: `lib.threat.classify`'s `RESOURCE_LIMITS`/`SUBPROCESS_EXEC` diff hints and
`lib.defect_shapes`'s new scans were reading *test* code (a `mod tests { ... }` block's
helper functions, `oneway::channel()` fixtures, `.unwrap()` in test setup) as if it were
production code -- the org's own real convention explicitly permits exactly the shapes
that were being flagged ("No unwrap()/expect() outside tests"). Both this run's own
fixtures and Phase 3's were reclassified after the fix; see
`lib/defect_shapes.py::added_lines_excluding_test_scope` and this sprint's `LEDGER.md`
entry for the exact fix. Re-classifying is not moving the goalposts after seeing an
inconvenient result -- KT-14.1's own question is reproducibility, not the sign of any
count, and the fix was found and applied before this document's numbers were finalized,
not after judging whether they were convenient.

| Task | Runs succeeded | Per-class counts across successful runs (post-fix) |
|---|---|---|
| `lopi-bound-unbounded-channels` | 2/3 (run1: exit 0, empty diff) | all classes 0 -- **identical on both successful runs** |
| `lopi-explicit-whatsapp-dev-override` | 3/3 | all classes 0 -- **identical on all three runs** |
| `lopi-typed-errors-sqlite-pool` | 3/3 | all classes 0 -- **identical on all three runs** |

Every successful run of every task in this kill-test, after the fix, is clean on every
mechanically-classified class -- confirming the fix did not regress detection on real
defects (the agent genuinely fixed the channel-bounding and error-typing tasks it was
asked to fix; `evals/gen_fixtures/04`-`06`'s hand-authored, deliberately-unmitigated
fixtures still fire their target classifier, per
`tests/test_genfixtures.py::test_new_fixtures_fire_their_target_class`, which stayed
green through this fix).

`raw_index_external_input` reads `None` (not 0) on every run, correctly, per KT-14.2's
fix earlier this sprint -- this task set never exercises that class, and the classifier
correctly never claims to have checked it.

**Agreement, stated as a number**: of the 3 tasks × 7 mechanically-classified classes =
21 mechanically-meaningful cells with 2+ successful repeats, **21/21 (100%) agree
exactly across every successful repeat** -- both before and after the classifier fix
(the pre-fix data also agreed with itself run-to-run; the fix changed *what* was found,
not whether repeats agreed with each other).

**The one real non-reproducibility this run found**: `lopi-bound-unbounded-channels`
run 1 exited 0 but produced no diff at all (confirmed: `git diff --cached` empty in
that run's worktree before cleanup). This is generation-layer variance (did the agent
do anything this time), not classifier-layer variance (did two existing diffs get
classified differently) -- a real, honestly-reported 1-in-9 session that produced
nothing to classify, distinct from the question this kill-test is actually gating.

## Reading the result against the pass condition

The kill-test's pass bar is "agreement high enough that a 3-run protocol can
distinguish a real effect from noise at the sample sizes Phase 3 can afford." At n=8
successful runs across 3 tasks, observed classification agreement is 100% -- there is
no measured noise floor for Phase 3's comparison to clear, which is the strongest form
of this pass condition, not a marginal one. The honest caveat: n=8 successful runs is a
small sample, and "0% observed disagreement" is a stronger claim at n=800 than at n=8.
This kill-test does not claim the classifier will always agree at scale -- only that at
the scale this session could afford to test, it did, with the specific failure mode
that did appear (a session producing no diff) named rather than hidden inside a vaguer
"variance" number.

## Decision

**Phase 3 proceeds** (the Stop Rule's condition is met). See
`.konjo/killtests/P14/phase3-report.md` for what Phase 3 actually ran this
session and, honestly, what it did not -- the full 12-20 task × 3 run × 6 candidate
protocol (up to ~250+ sessions once every candidate is measured individually) is not
affordable inside this session on top of the harness-building, classifier, and
gate-ramp work also required this sprint; Phase 3 runs a real, smaller slice and states
the reduction plainly rather than silently shrinking scope, per this project's own
established precedent for exactly this situation.
