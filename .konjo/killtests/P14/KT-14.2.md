# KT-14.2 -- Does the classifier launder an unknown class into a zero?

**Verdict: FAIL on first run, FIXED in this sprint, PASS on re-run.** Not a clean pass
from a cold read -- a real instance of the exact failure shape this kill-test exists to
catch, found by actually tracing a known-unclassified class through every layer of the
reporting path, not by inspection alone.

## Procedure

Feed `konjo-eval gen`'s corpus (which always carries at least one genuinely
unclassified class -- `raw_index_external_input`, see `evals/genfixtures.py`'s
`MECHANICALLY_CLASSIFIED` comment) through every downstream layer and inspect each
output for whether `None` (not checked) stays visibly distinct from `0` (checked,
clean):

1. `ClassificationResult.findings` (single-diff classification)
2. `run_gen_corpus`'s `totals` dict (cross-fixture aggregation)
3. `bin/konjo-eval gen`'s human-readable print
4. `bin/konjo-eval gen --json`'s machine-readable output

## What was found

Layers 1, 3, and 4 were clean: `ClassificationResult.count()` returns `None` for an
unclassified class (never coerced to an int), the human printer's per-fixture line
correctly omits both `None` and `0` findings (indistinguishable in that compact view,
which is fine -- the `NOT mechanically classified by this harness` line beneath it names
the unclassified set explicitly and unconditionally), and the JSON layer just serializes
whatever Python object it's given.

**Layer 2 failed.** `run_gen_corpus` (pre-fix, shipped since 1.8.0's Phase 4)
initialized `totals: dict[str, int] = {c: 0 for c in DEFECT_TAXONOMY}` and only
incremented entries for classes that returned a real count -- an unclassified class's
`totals[c]` stayed at its initial `0` forever, identical in shape and value to "checked
across every fixture in the corpus, zero defects found." Confirmed directly:

```
$ python3 bin/konjo-eval gen
  totals: unconfigured_permit_branch=0, unbounded_queue=1, missing_timeout=2,
          raw_index_external_input=0, ...
```

`raw_index_external_input=0` here read exactly like a clean bill of health. A consumer
reading only `report["totals"]` (the JSON layer's most natural entry point -- exactly
what a future Phase 3 aggregation script would do) had no way to tell "zero defects"
from "never checked" without also cross-referencing `unclassified_classes`, a second
field this project's own `konjo-eval gen` human printer already knew to check but
nothing enforced a caller must. This is the same shape `gate_polarity` exists to catch
in application code (a default/fallback path reading as a pass), reproduced inside the
instrument built to measure whether `gate_polarity`-shaped invariants help.

## The fix

`totals` now initializes every class to `None`, the same as a single fixture's
`ClassificationResult`, and only becomes an `int` once at least one fixture actually
returns a real count for it (`totals[c] = (totals[c] or 0) + n`). A mechanically
classified class always turns into an int (every fixture classifies it, by
construction); an unclassified class stays `None` through the whole aggregation,
matching every other layer. Re-run after the fix:

```
$ python3 bin/konjo-eval gen --json | jq .totals
{
  "unconfigured_permit_branch": 0,
  "unbounded_queue": 1,
  "missing_timeout": 2,
  "raw_index_external_input": null,
  ...
}
```

`null` now reads unambiguously as "not measured" at every layer, including the one
that failed. Regression test: `tests/test_genfixtures.py::
test_run_gen_corpus_totals_none_stays_none_for_unclassified_class` and
`test_run_gen_corpus_empty_dir_is_report_only_zero` (a zero-fixture corpus now asserts
every class is `None`, not `0` -- zero fixtures means zero classification happened, so
"0 defects" would have been a second instance of the same false claim).

## Decision

**Fix before any measurement runs**, per this kill-test's own instruction. Phase 3's
per-class defect counts (this sprint or a future one) read `run_gen_corpus`'s `totals`
directly -- had this shipped unfixed, every future Phase 3 report table would have
silently claimed "zero `raw_index_external_input` defects" as if the harness checked
for them, for every context compared, forever. Caught here because KT-14.2 asked the
procedure to trace the value through the aggregation layer specifically, not just the
single-diff classifier Phase 13 already verified.
