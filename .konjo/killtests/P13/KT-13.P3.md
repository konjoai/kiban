## What actually separates them

Identical mechanism to `gate_one_way_door`/`gate_prove`: a stable fingerprint over the
sorted changed-file set (`oneway.fingerprint`, no new fingerprint scheme), a commit
trailer (`Konjo-Threat-Model: <fp>`, built and checked via `oneway.make_trailer`/
`find_trailer`, no second override channel), and a CI gate that only greps `git log
base..HEAD` for that trailer -- it never re-runs `threat.classify` or inspects the recorded
mitigation/abuse-case content. The content-quality check (real mitigation, real abuse
case, a taxonomy-valid boundary name) happens once, at record time, session-side --
exactly where `confirm.confirm_one_way` enforces its own token-and-justification
requirement, and for the same reason: CI must stay a cheap grep, not a second copy of the
judgment call.

## Rescope decision

Ships as a real blocking gate (no advisory toggle), unlike `gate_polarity`/
`gate_claude_contract`'s adoption ramp. Reasoning: `security_globs` is opt-in per profile
(default: SKIP for any repo that hasn't declared or matched the default glob set), so
there is no existing-repo baseline to "clean up" the way an always-on doc contract or a
codebase-wide pattern scan has -- a profile that turns this on is doing so for new/changed
work going forward, not retroactively against history it doesn't control.

## Limit carried forward

Same class of limit as `gate_can_fail`: this gate verifies a threat model was *recorded*
with real (non-empty, taxonomy-valid) content -- it cannot verify the mitigation is the
*right* mitigation, or that the abuse case is the *hardest* one, any more than
`gate_can_fail` can verify a `rejects_test` command exercises the hard input rather than
the easy one. Both limits are named in their own gate's docstring rather than silently
shipped past, per `KONJO_FORWARD.md`.
