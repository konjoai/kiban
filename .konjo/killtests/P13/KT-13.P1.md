## What actually separates them

The section-order check is pure heading-prefix matching (`REQUIRED_SECTIONS`, matched
case-insensitively by prefix so a repo can extend a heading's title without breaking the
contract). The enforcement check is shape, not content: any bullet under an
invariants/hard-rules heading that doesn't contain `gate_x`, `repo:x`, `konjo-x`, or the
literal word `ADVISORY` is flagged -- it does not attempt to verify the named gate
actually exists or actually checks that claim (that would require a model or a live
registry lookup; this gate stays offline by design, the same boundary `gate_can_fail`
draws for `rejects_test` commands).

## Rescope decision

Ships advisory (WARN) by default, same ramp as `gate_polarity`: a repo's existing
CLAUDE.md is very unlikely to already be in contract (lopi's, read this sprint, is not --
see the `LEDGER.md` entry), so blocking on adoption day would fail every repo
immediately. `claude_contract.advisory: false` promotes it once a repo's CLAUDE.md has
been converted.

## Limit carried forward

The enforcement-naming check cannot verify a named gate actually exists in this repo's
gate set, or that it actually enforces the claimed invariant -- it only checks that
*something shaped like a gate reference* is present. A bullet that says "(enforced:
gate_nonexistent)" passes. Closing that gap would require cross-referencing the profile's
declared gates and `konjo-gates`' real gate list, which is a meaningfully larger check
(and arguably belongs nearer `gate_can_fail`, which already does real
existence-and-passing verification for a different class of claim -- `rejects_test`
commands). Left as a known limit, matching this project's own convention of naming a
limit rather than silently shipping past it (`KONJO_FORWARD.md`).
