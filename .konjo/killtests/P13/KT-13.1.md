# KT-13.1 -- Can a defect rate be produced for the current authoring context, by class, reproducibly?

**Verdict: NOT EXECUTED AT SPECIFIED RIGOR.** This is not a PASS and not a scientific
FAIL (variance swamping effect, or an inconsistently-applied taxonomy) -- it is a third,
honestly-distinct outcome: the infrastructure the procedure depends on does not exist,
and building it well enough to run 3 full passes over a 12-20 task holdout set inside
this session would trade rigor for speed in exactly the way this kill-test exists to
catch. Per the sprint's own Stop Rule, this has the same practical consequence as a
FAIL: **Phase 2 does not ship.** Phases 0, 1, 3, and 4 proceed on their own merits, as
the brief explicitly allows.

## What the procedure requires

1. A held-out set of 12-20 small implementation tasks drawn from real closed work
   (git log, not invented) across lopi, squish, and vectro.
2. Each task run under the current always-on context via `konjo-headless`, three full
   times, with the resulting diff classified against the fixed eight-class defect
   taxonomy.
3. Per-class counts stable enough across the three runs that a change the size Phase 2
   expects would be visible, with the observed variance stated.

## What was checked before attempting this

Read `bin/konjo-headless` and `lib/headless.py` in full (132 lines total). Finding:
`konjo-headless` is a thin wrapper over `claude -p <prompt> --bare --output-format
stream-json`, returning raw text/stream-json. It has **no notion of "task description
in, diff out"** -- no repo checkout, no diff capture, no apply/verify loop. It is a
generic headless-prompt primitive other tooling is meant to build on, not an
implementation-task harness. Confirmed by grep and read: **nothing in the repo today
runs the loop KT-13.1's procedure assumes** ("run each task, capture the diff").

## Why this was not built-and-rushed instead

The honest options were: (a) build the missing harness properly and then decline to run
the full 36-60-invocation protocol (12-20 tasks × 3 runs, each a real autonomous
coding session against a real crate, each requiring careful classification against the
taxonomy) inside one session already carrying five other phases of real engineering
work, or (b) build a truncated version -- fewer tasks, one run each, classification done
quickly -- and report it as if it satisfied KT-13.1. (b) is precisely the failure mode
this kill-test's own FAIL clause names: "the taxonomy cannot be applied consistently."
A taxonomy applied once per task by a single rushed pass, with no repeat runs to check
classification stability against the classifier's own noise (not just the generator's),
is not evidence of a stable per-class count -- it is a number with the *appearance* of
rigor and none of its substance. Reporting it as a KT-13.1 PASS or FAIL would be the
unfalsifiable claim `KT-13.1`'s own preamble warns against making.

## What was built instead (real, not a workaround)

Phase 4 ("Generation fixtures in the eval harness") needed this harness anyway -- its own
motivation paragraph names the same gap: *"Nothing tests whether the authoring context
prevents [a bad diff]. That gap is why Phase 2 needs building before it can measure
anything."* So the harness is built for real in this sprint (see `evals/genfixtures.py`,
`bin/konjo-eval`'s new `gen` subcommand), seeded with a small illustrative corpus (3
tasks, drawn from real closed lopi commits per `git log`, one run each -- clearly marked
`illustrative`, not a KT-13.1 run) to prove the mechanism end-to-end offline. This is
real, reusable infrastructure, not a substitute measurement.

## What a real KT-13.1 run requires next

1. A held-out task set assembled from closed PRs/commits in lopi, squish, and vectro --
   git log is already available for lopi (`b93e68f` at time of writing) and squish/vectro
   are reachable via `list_repos`/`add_repo`, not yet cloned this sprint.
2. Budget for 36-60 real `konjo-headless`-driven implementation sessions (12-20 tasks ×
   3 runs), each producing a diff to classify.
3. A defect classifier -- either a dedicated review pass per diff (reusing
   `lib/review.py`'s specialist machinery scoped to the eight-class taxonomy) or a
   human/model rubric pass -- run consistently across all runs so classification noise
   doesn't get conflated with generation noise.
4. This is squarely a `konjo-eval gen` job once (1) exists as real fixtures -- the
   harness built this sprint is the prerequisite, not a placeholder.

## Decision

Ship Phases 0, 1, 3, 4, 5, 6. Do not ship Phase 2 (no invariant added to the always-on
context this sprint) -- there is no measured defect delta to justify any of the six
candidates, and KT-13.2 passing (room exists) is necessary but not sufficient without
KT-13.1's evidence. The six candidates and their rationale are recorded in `LEDGER.md`
as **not measured, not added**, for the next session to pick up once the harness this
sprint built has run for real.
