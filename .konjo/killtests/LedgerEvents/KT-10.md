# KT-10 -- Do two surfaces adding events concurrently merge cleanly?

## Pre-registration (write this section BEFORE running anything)

Claim under test: two surfaces adding events simultaneously merge cleanly, because
each event is its own file (Sprint K5's whole rationale for the per-file store,
`Ledger-Events-Per-File-1` in `LEDGER.md`).

Method: a throwaway local git sandbox (a bare repo as a fake origin, two independent
clones -- no real repo touched, no network) --

- **Leg 1 (events only).** From `clone-a` and `clone-b`, each add one new event file
  under `ledger/events/` (distinct ids), without pulling the other's change first.
  Push `clone-a`; `clone-b`'s push should be rejected (non-fast-forward); merge
  `clone-b` against the updated `origin/main` and push again.
- **Leg 2 (events + refold).** Same shape, but each clone also rewrites the same
  derived page file (`repo-demo.md`) to reflect its own new event -- simulating what
  `konjo-decision decide`'s inline fold step (Phase 2) actually does on every write.

Threshold: event files merge with zero conflicts in both legs. Page conflicts in Leg
2 are expected and acceptable -- pages are derived and regenerable, per the brief.

Stop rule: if event files conflict in either leg, the per-file design has failed and
the sprint stops -- this is not a result to explain away with a smarter merge
strategy, it means the core claim (separate files never conflict) is false. If page
conflicts turn out painful rather than merely expected, the fix is to stop
committing pages and let CI generate them on demand, which is a different sprint (not
attempted here).

## Absence-of-evidence check

Not applicable in the strict sense (this test's verdict rests on git's own merge
output -- an observed exit code and an observed absence of `<<<<<<<` markers in the
event files -- not on a tool silently returning nothing). The positive control below
still applies: a mechanism that always reports "no conflict" is exactly as useless as
a search that always returns `[]`.

## Positive control

The mechanism must be shown capable of producing a *real* conflict on the same data,
by the same method, or the "zero conflicts" reading is not trustworthy. Leg 2 is that
positive control by design: both clones intentionally rewrite the same page file
(`repo-demo.md`), and the test asserts that conflict *does* occur there (git exits
non-zero, `<<<<<<<` markers appear) at the same time it asserts the event files in
the same commits merge clean. Seeing both outcomes in the same run is what makes
Leg 1's "zero conflicts" a demonstrated property of per-file events specifically, not
an artifact of a merge strategy that never reports conflicts at all.

## Method

All commands run from `/tmp/kt10` (a scratch sandbox, not `konjo-cortex` or any real
repo). Full transcript:

```bash
git init --bare -q -b main /tmp/kt10/origin.git
git init -q -b main /tmp/kt10/seed && cd /tmp/kt10/seed
mkdir -p ledger/events
# ledger/events/base000000001.json -- one seed decide event
# repo-demo.md -- "seed page"
git add -A && git commit -qm seed
git remote add origin /tmp/kt10/origin.git && git push -q -u origin main
git clone -q /tmp/kt10/origin.git /tmp/kt10/clone-a
git clone -q /tmp/kt10/origin.git /tmp/kt10/clone-b

# Leg 1: each clone adds one event file only.
# clone-a: ledger/events/aaaaaaaaaaaa.json, commit, push (first -- succeeds).
# clone-b: ledger/events/bbbbbbbbbbbb.json, commit, push (rejected, non-fast-forward).
# clone-b: git fetch && git merge --no-edit origin/main -- then push.

# Leg 2: each clone adds one more event file AND rewrites repo-demo.md.
# clone-a: ledger/events/cccccccccccc.json + repo-demo.md edit, commit, push (succeeds, first).
# clone-b: ledger/events/dddddddddddd.json + repo-demo.md edit, commit, push (rejected).
# clone-b: git fetch && git merge --no-edit origin/main.
```

## Stop rule

A green exit code from `git push`/`git merge` alone is not sufficient -- it has to be
paired with actually inspecting the working tree for `<<<<<<<` conflict markers
(`grep -rl '^<<<<<<<' .`) and confirming every expected file (both new event ids, in
both legs) is actually present after the merge, not silently dropped by an
auto-resolution. A merge that "succeeds" by discarding one side's file would pass a
naive exit-code check and still be a real failure of the per-file design.

## Grading anything that runs outside this session

Not applicable -- every command in this test ran directly in this session against a
local sandbox; nothing was delegated to a spawned session or fired routine.

---

# Verdict: PASS, both legs (2026-08-19)

## Leg 1 (events only)

```
=== clone-a push (first, should succeed cleanly) ===
clone-a push OK
=== clone-b push (should be rejected, non-fast-forward) ===
git push exit code: 1

$ git fetch -q origin && git merge --no-edit origin/main
Merge made by the 'ort' strategy.
 ledger/events/aaaaaaaaaaaa.json | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 ledger/events/aaaaaaaaaaaa.json
merge exit code: 0

$ grep -rl '^<<<<<<<' . --include="*"
none found

$ find ledger/events -type f | sort
ledger/events/aaaaaaaaaaaa.json
ledger/events/base000000001.json
ledger/events/bbbbbbbbbbbb.json
```

`clone-b`'s push after the merge succeeded, and `clone-a` pulling afterward folded
all three events correctly (`ledger.engine.Ledger` + `lib.cortex.render_scope` over
the merged `ledger/events/` directory produced all three decisions active, in the
right order). **Zero event conflicts, both new ids present, fold correct.**

## Leg 2 (events + refold)

```
$ (clone-a) git push -q origin main
clone-a Leg2 push OK

$ (clone-b) git fetch -q origin && git merge --no-edit origin/main
Auto-merging repo-demo.md
CONFLICT (content): Merge conflict in repo-demo.md
Automatic merge failed; fix conflicts and then commit the result.
Leg2 merge exit code: 1

$ git status --short
A  ledger/events/cccccccccccc.json
UU repo-demo.md

$ grep -l '^<<<<<<<' ledger/events/*.json
none -- event files merged cleanly

$ find ledger/events -type f | sort
ledger/events/aaaaaaaaaaaa.json
ledger/events/base000000001.json
ledger/events/bbbbbbbbbbbb.json
ledger/events/cccccccccccc.json
ledger/events/dddddddddddd.json
```

**Event files: zero conflicts, both new ids (`cccccccccccc`, `dddddddddddd`)
present -- `cccccccccccc.json` auto-staged (`A`) by git's own three-way merge with no
human intervention. Page file: exactly one conflict, in `repo-demo.md`, as predicted
by the positive control.**

## Both legs pass. Headline numbers.

- Leg 1 event-file conflicts: **0**. Leg 1 page conflicts: not exercised (Leg 1
  deliberately doesn't touch the page).
- Leg 2 event-file conflicts: **0**. Leg 2 page conflicts: **1** (`repo-demo.md`,
  expected and acceptable per the brief).

## What this does and does not establish

Establishes: the per-file event format's core claim -- two surfaces adding distinct
events never conflict, even when both also touch a shared derived page in the same
commit -- holds under a real git merge, not just by inspection of the design. The
positive control (Leg 2's page conflict) confirms this isn't because the test setup
can't produce a conflict at all.

Does not establish: behavior at scale (this test used 2 clones and 2-4 events total,
not the "thousands of events" ceiling `ledger/schema.md` already names as untested
and out of scope), behavior with three or more concurrent writers, or behavior on the
real `konjo-cortex` repo specifically (this ran in a disposable sandbox, deliberately,
to avoid polluting real repo history with scratch commits). Nothing here required
`KONJO_CORTEX_DIR`, `konjo-decision`, or any kiban CLI -- it is a property of git
merging distinct files, which per-file storage exists specifically to invoke.
