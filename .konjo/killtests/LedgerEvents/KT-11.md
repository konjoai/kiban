# KT-11 -- Does a decision logged from the phone actually appear in Cortex?

## Pre-registration (write this section BEFORE running anything)

Claim under test: a decision logged from the phone (Claude Cowork, via a task or
Routine) appears in `konjo-cortex`, and is readable from the laptop after a pull.

Threshold: the event lands, the fold runs, the page updates, and the laptop sees it
after a pull -- all four, not just the write.

Stop rule (from the brief, restated exactly): if the phone can read but not write,
say so plainly and scope the sprint to laptop-and-cloud writes. That is still a large
improvement and a partial result is better than an overclaimed one.

**Stated before attempting anything: this session has no path to a real phone.** This
is a cloud sandbox session with terminal/tool access only -- no device control, no
Cowork mobile client, nothing that could drive an actual phone through
`konjo-decision decide`. This is named up front, not discovered as a surprise after
trying and failing, because the template's own worked precedent (`KT-3`'s original
run) is exactly the failure mode of treating "I couldn't find a way" as equivalent to
"I tried the real mechanism and it didn't work." Those are different findings and
this test does not conflate them.

## Absence-of-evidence check

1. **What tool or assumption is the negative resting on?** The absence of any device
   -control or mobile-client tool in this session's available tool set. Checked
   directly, not assumed: this session's tool list was reviewed for anything phone-
   or device-adjacent (computer-use/device-control tools exist for *desktop* browser
   automation in some Claude Code configurations, per this repo's own
   `.claude/skills/` references to `mcp__remote-devices__computer_*`-style tools
   elsewhere in the Konjo ecosystem) -- no such tool is present in this session.
2. **What was it expected to enumerate, and is that documented or assumed?** Whether
   a phone-driving capability exists for *this specific session*, not whether one
   exists anywhere in the Konjo/Cowork product surface generally (it does, per
   `gemini-computer-use-image-gen`-style skills referenced in other sessions' tool
   catalogs -- that capability is real, just not present here).
3. **Flagged as unconfirmed for the actual claim** (does a real phone write and sync
   correctly) **and confirmed for the narrower claim this session can actually
   test** (structural/mechanism identity between the phone and cloud write paths,
   both of which run the same code with no invocation-surface branch).

## Positive control

Not run, and not claimed. A positive control here would mean demonstrating this
session *can* drive a phone for at least one other action, to prove the absence
above isn't a search-scope mistake. This session did not attempt that, because the
tool catalog check in the absence-of-evidence section is definitive on its own (a
fixed list of available tools, not a search that could miss something) -- unlike
`KT-3`'s original `ListConnectors` case, there is no ambiguity a positive control
would resolve here. Recorded as a deliberate skip, not an oversight.

## Method

What this session *did* verify, as the honest substitute for the real test:

1. Read `bin/konjo-decision`'s `decide`/`supersede`/`redact` handlers end to end
   (Sprint K5 Phase 2 changes, this same PR) to confirm the write path has no branch,
   prompt, or dependency on an interactive terminal, a specific OS, or a specific
   invocation surface -- it is a single Python process that reads
   `KONJO_CORTEX_DIR`, writes one event file, then best-effort folds/commits/pushes
   (`lib/cortex_sync.py`). Nothing in that path distinguishes "invoked by a human
   typing in a laptop terminal" from "invoked by a Cowork task running on a phone" or
   "invoked by a fired Routine in a cloud session" -- the same binary runs unmodified
   in all three.
2. Confirmed this structural identity is the same property Phase 2's cloud write
   path already relies on (this very session wrote real events into a local
   `konjo-cortex` clone via this exact code path, see `Ledger-Laptop-Only-1` /
   `Ledger-Events-Per-File-1` in `LEDGER.md` and the migration work in this PR) --
   the phone path is not new code, it is the same code on a different device.
3. Did **not** attempt to fabricate a phone run, simulate one, or describe a
   structural argument as if it were an executed test. The distinction matters: "the
   code has no surface-specific branch" is real evidence for *transferability*, not
   evidence that the actual mechanism (Cowork on an actual phone, actual mobile
   network, actual GitHub push from that context) works end to end.

## Stop rule

A structural/code-reading argument is not sufficient to claim PASS on this test's
actual claim, no matter how confident the reasoning -- this is exactly the "session
status alone" failure mode the template warns against, just at one more remove (code
review instead of a session's IDLE status). The only thing that closes this test is
someone running `konjo-decision decide` for real from an actual phone and confirming
the four-part threshold above.

## Grading anything that runs outside this session

Not applicable to this session's own portion (nothing was delegated or fired); fully
applicable to how Wes should grade his own run when he does this for real: don't
trust "Cowork said it worked" -- pull the laptop's `konjo-cortex` clone afterward and
read the actual new page content, the same standard this test applies to itself.

the stop rule stated above and the brief's own instruction ("if the phone can read
but not write, say so plainly and scope the sprint to laptop-and-cloud writes"), this
verdict scopes even further down: **this session verified neither read nor write from
an actual phone**, because it has no mechanism to drive one. What it does report,

  `konjo-decision decide`/`supersede`/`redact` (Sprint K5 Phase 2, this PR) contains

  migration/reconstruction work elsewhere in this PR) is what a phone-driven Cowork
  task or Routine would invoke.
- **Not verified: the actual phone run.** Real device, real Cowork task, real
  network, real GitHub push, real laptop pull-and-read -- none of that happened in
  this session, and no output above should be read as a substitute for it.

**Sprint scope, per the stop rule:** this sprint's headline claim narrows to
**laptop-and-cloud writes verified** (Phase 2's own write-path testing, this PR), with
the **phone leg specifically outstanding**, not silently assumed to work because the
code looks like it should. This is the honest-negative-result the org's own
"evidence first, honest negative results" standard calls for over a confident
structural argument dressed up as a PASS.
